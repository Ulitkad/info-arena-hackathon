# Инфо Арена

[English version](README.md)

Инфо Арена - MAX-бот и Mini App для геймификации обучения. Приложение поддерживает задания, мероприятия, Battlepass, награды, друзей и дуэли.

Frontend написан на Vue 3, Vite, Pinia и Vue Router. Backend использует FastAPI, SQLAlchemy 2, SQLite и Alembic.

## Возможности

- **Ученик:** вступление в учреждение по приглашению, сдача и доработка заданий, запись на мероприятия, общий и предметные Battlepass, достижения, друзья и дуэли.
- **Преподаватель:** создание и проверка заданий, управление мероприятиями и участниками в рамках назначенной нагрузки "предмет - группа".
- **Управляющий:** управление группами, предметами, заявками, преподавателями, нагрузкой, приглашениями и наградами учреждения.
- **Администратор:** управление учреждениями, назначение управляющих и администрирование выбранного учреждения.
- Уведомления внутри приложения и через WebSocket. Фоновые задачи проверяют дедлайны и завершают дуэли каждые 30 секунд.

## Требования

Команды ниже рассчитаны на Bash в Debian-based Linux и запускаются из корня репозитория.

- Python 3.11 или новее
- uv 0.9 или новее
- Node.js 22.12 или новее, либо Node.js 24 LTS
- npm
- Docker Engine и плагин Docker Compose v2 для контейнерного развёртывания

На минимальной Debian- или Ubuntu-системе установите зависимости Python:

```bash
sudo apt update
sudo apt install -y python3 ca-certificates curl
```

Установите поддерживаемую версию Node.js подходящим для дистрибутива способом. Перед запуском проверьте версии:

```bash
python3 --version
node --version
npm --version
```

## Локальный запуск без MAX

Установите зависимости backend через `uv` (он создаёт и управляет
`backend/.venv` по `pyproject.toml` и `uv.lock`):

```bash
uv sync --directory backend
```

Создайте `backend/.env` с локальными параметрами. Не используйте в этом файле Docker-пути `/data`.

```dotenv
SECRET_KEY=REPLACE_WITH_A_RANDOM_SECRET_AT_LEAST_32_CHARACTERS_LONG
DATABASE_URL=sqlite+aiosqlite:///./data/arena.db
UPLOAD_DIR=uploads
BASE_APP_URL=http://localhost:5173
DEV_AUTH=true
SEED_DEMO=true
```

Сгенерировать подходящий секрет можно так:

```bash
uv run --directory backend python -c 'import secrets; print(secrets.token_urlsafe(48))'
```

Запустите API в первом терминале:

```bash
uv run --directory backend alembic upgrade head
uv run --directory backend uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Во втором терминале, начиная из корня репозитория, запустите frontend:

```bash
cd frontend
npm ci
npm run dev -- --port 5173 --strictPort
```

Откройте <http://localhost:5173>. При включённой демо-авторизации страница входа предоставляет демо-пользователей для ролей ученика, преподавателя, управляющего и администратора. Для смены пользователя выйдите через кнопку в шапке.

Полезные адреса:

- Проверка API: <http://localhost:8000/api/health>
- Swagger UI: <http://localhost:8000/docs>
- Vite проксирует `/api`, `/media` и `/ws` на API, поэтому для локальной разработки отдельная настройка CORS не нужна.

Демо-авторизация включается только при одновременных `DEV_AUTH=true` и `SEED_DEMO=true`. Она открывает доступ ко всем демо-ролям и не должна использоваться на публичном сервере. Для реальных данных используйте отдельную базу. Переменные окружения процесса имеют приоритет над значениями из `.env`.

## Развёртывание через Docker Compose

Приложение поставляется **одним образом** `ulitkad/info-arena:latest`:
frontend, Nginx, FastAPI, планировщик и MAX-бот работают в одном контейнере под
управлением Supervisor, от непривилегированного пользователя UID 10001.
Внешний порт контейнера — `8080`, healthcheck — `/api/health`.

На сервере нужны только Docker Engine с Compose v2 и **два файла в одном каталоге**:

```text
compose.yml
.env
```

Исходники, Dockerfile, Node.js, Python и конфигурации Nginx на сервер не нужны.
Образ должен быть уже опубликован в Docker Hub. Для первого запуска возьмите
`compose.yml` и скопируйте `.env.example` в `.env`:

```bash
cp .env.example .env
```

Адрес образа `ulitkad/info-arena:latest` зафиксирован в `compose.yml`.
В `.env` укажите постоянный случайный `SECRET_KEY` длиной не менее 32 символов.
Создать секрет:

```bash
openssl rand -hex 32
chmod 600 .env
```

Для **локальной проверки хакатона** задайте `DEV_AUTH=true`, `SEED_DEMO=true`,
оставьте `BOT_TOKEN` пустым и `WEB_BIND_ADDRESS=127.0.0.1`. После запуска войдите
через демокнопки ученика, преподавателя, управляющего и администратора.
Деморежим нельзя включать на публичном сервере. Для реального MAX используйте
`DEV_AUTH=false`, `SEED_DEMO=false`, токен бота и публичный HTTPS `BASE_APP_URL`.

Запуск из каталога с двумя файлами (для публичного образа `docker login` не нужен):

```bash
docker compose pull
docker compose up -d --wait
docker compose ps
curl --fail http://127.0.0.1:8080/api/health
docker compose logs -f app
```

Приложение доступно по адресу <http://localhost:8080>. Порт хоста задаётся
`WEB_PORT`, адрес привязки — `WEB_BIND_ADDRESS` (по умолчанию `127.0.0.1`, только
локальный доступ). Для прямого доступа с других машин задайте `0.0.0.0` и
настройте firewall. `BASE_APP_URL` должен соответствовать адресу приложения.

При каждом старте сначала применяются миграции Alembic. При их ошибке контейнер
не запускает HTTP-сервер. Затем запускаются один API worker с планировщиком,
Nginx и один polling-бот. Без `BOT_TOKEN` бот остаётся неактивным. Логи всех
процессов доступны через `docker compose logs`. Healthcheck проверяет frontend
и API через Nginx; он не подтверждает доступность внешнего MAX API.

SQLite и загруженные файлы хранятся в именованных volumes `database` и `uploads`.
Обычный `docker compose down` сохраняет данные. **Не используйте `down -v`, если
данные нужны.** Не меняйте каталог развёртывания или имя Compose-проекта без
переноса volumes. Перед обновлением создайте согласованную резервную копию
SQLite при остановленном приложении или через SQLite backup API, а также uploads.

Обновление: дождитесь успешной публикации нового `latest` и выполните:

```bash
docker compose pull
docker compose up -d --wait
```

Не меняйте `SECRET_KEY` при обновлении. `latest` перезаписывается при каждой
публикации; для фиксации сданной сборки сохраните digest образа. Откат образа
не откатывает миграции базы. Обновление может вызвать краткий перерыв в работе.

Встроенный Nginx работает по HTTP. Для production Mini App нужен внешний HTTPS
reverse proxy с корректной цепочкой сертификатов, проксированием `/ws` и
`BASE_APP_URL=https://...`. При прокси на хосте оставьте привязку `127.0.0.1`.
Прокси в отдельном контейнере требует общей Docker-сети или другого доступного
адреса: его `127.0.0.1` не указывает на приложение.

### Сборка единого образа из исходников

Из корня репозитория:

```bash
docker build -t info-arena:local .
sh docker/smoke-test.sh info-arena:local
```

Smoke test использует отдельные временные volumes и демосекрет, проверяет
frontend, SPA-маршруты, API, все демороли, запрет скрытых файлов и повторный
старт с сохранёнными данными. Рабочий `.env` не читается, тестовые volumes удаляются.

Для запуска локально собранного образа через основной Compose:

```bash
docker tag info-arena:local ulitkad/info-arena:latest
```

Выполните `docker compose up -d --wait --pull never` (без `docker compose pull`).
Это использует локальный образ вместо скачивания опубликованного `latest`.

### Публикация через GitHub Actions

Создайте публичный репозиторий Docker Hub `ulitkad/info-arena`.
В GitHub → Settings → Secrets and variables → Actions добавьте:

- Repository secret `DOCKERHUB_TOKEN` — Docker Hub PAT аккаунта `ulitkad` с правами Read & Write.

Workflow `.github/workflows/docker-publish.yml` при push в `main` запускает тесты,
собирает образ, проверяет демозапуск и перезапуск на `amd64`, затем публикует
единый образ для `linux/amd64` и `linux/arm64`. Реальный MAX при этом не проверяется.
Push в `main`, push тега `v*` и ручной запуск workflow публикуют
`ulitkad/info-arena:latest`. Логин и тег зафиксированы в workflow и Compose;
дополнительные GitHub Variables и переменные образа в `.env` не нужны.

Передайте проверяющим адрес образа `ulitkad/info-arena:latest`, `compose.yml`,
безопасный `.env.example` и инструкцию демозапуска. Рабочий `.env`, токены и базы
передавать не нужно. Логин в адресе образа публичный и не является секретом.

### Переход со старого Compose

Ранее стек использовал отдельные `api`, `web`, `bot` в `compose.yaml`.
Остановите старый стек **до** замены файла, без `-v`, и сделайте бэкап.
Используйте тот же каталог/имя проекта и те же volumes; запустите новый
`compose.yml`. Одновременно старую и новую версии запускать нельзя: они будут
делить SQLite и токен polling-бота. Не оставляйте рядом старый `compose.yaml`:
Compose предпочитает его файлу `compose.yml`.

## Переменные окружения

Файл конфигурации читается относительно текущего рабочего каталога. При локальном запуске API из `backend` используется `backend/.env`; Compose передаёт сервисам корневой `.env`.

| Переменная | Назначение |
| --- | --- |
| `WEB_PORT` | HTTP-порт хоста; по умолчанию `8080`. |
| `WEB_BIND_ADDRESS` | По умолчанию `127.0.0.1`; `0.0.0.0` открывает порт на всех IPv4-интерфейсах. |
| `SECRET_KEY` | Обязательный случайный секрет JWT длиной не менее 32 символов. Все экземпляры API должны использовать одно значение. После смены старые токены недействительны. |
| `DATABASE_URL` | Локально: `sqlite+aiosqlite:///./data/arena.db`. Compose фиксирует `sqlite+aiosqlite:////data/arena.db` для volume. |
| `UPLOAD_DIR` | Локально: `uploads`. Compose фиксирует `/uploads`, совпадающий с каталогом Nginx. |
| `BASE_APP_URL` | Публичный корневой адрес Mini App без завершающего `/`. Локальное значение: `http://localhost:5173`. |
| `BOT_TOKEN` | Токен MAX-бота. Храните его только на сервере, не во frontend. |
| `BOT_USERNAME` | Имя бота из `https://max.ru/<name>`, без `@` и URL. Используется в ссылках запуска и кнопке бота. |
| `ADMIN_MAX_ID` | Числовой MAX ID первоначального администратора. Роль назначается после проверенного входа через MAX. |
| `BOT_API_URL` | Базовый адрес MAX API. По умолчанию: `https://platform-api2.max.ru`. |
| `MAX_CA_BUNDLE` | Необязательный путь к доверенному PEM CA bundle, дополняющему системное хранилище сертификатов клиента. |
| `DEV_AUTH` | По умолчанию `false`. Только для локальной разработки. |
| `SEED_DEMO` | По умолчанию `false`. Требует `DEV_AUTH=true` и создаёт демоданные при запуске API. |

## Подключение MAX

1. Создайте бота в [MAX для бизнеса](https://business.max.ru/) и скопируйте его токен. Укажите `BOT_TOKEN`, `BOT_USERNAME`, `ADMIN_MAX_ID` и `BASE_APP_URL`.
2. Опубликуйте Mini App по HTTPS и укажите этот URL в настройках бота. Отключите демо-флаги и используйте чистую базу с применёнными миграциями.
3. Запустите API и frontend. При локальной разработке запустите бота отдельной командой из `backend`:

   ```bash
   uv run --directory backend python -m app.bot
   ```

   В едином контейнере процесс бота запускается автоматически.

4. Бот использует long polling, а не webhook. Не запускайте несколько экземпляров с одним токеном и не оставляйте активную webhook-подписку. Перед включением polling удалите старый webhook через MAX API.
5. Отправьте боту `/start` и откройте арену кнопкой. Пользователь без назначения получает статус ожидания. Первоначальный администратор создаёт учреждение и выбирает "Пригласить управляющего" в его карточке. Передайте будущему управляющему одноразовую ссылку; username или ID не требуется.
6. Управляющий создаёт предметы и группы, связывает их и создаёт одноразовое приглашение преподавателя с нужной нагрузкой. Нагрузку принятого преподавателя можно редактировать отдельно. Ученики вступают по многоразовым ссылкам групп, их заявки требуют одобрения.

При заданном `BOT_USERNAME` приглашения имеют вид `https://max.ru/<name>?startapp=<token>`. MAX передаёт токен в подписанном `start_param`. Без имени бота API возвращает обычную ссылку `BASE_APP_URL` с `group_token` или `invite_token`. Это удобно для локальной разработки, но обычная браузерная ссылка сама по себе не даёт авторизацию MAX.

Новая ссылка группы для учеников отзывает предыдущую. Приглашения преподавателей и управляющих строго одноразовые: после успешной активации ссылку нельзя использовать повторно, в том числе тем же аккаунтом. После активации обычный вход выполняется без ссылки-приглашения. Неиспользованные приглашения можно отозвать в интерфейсе. Приглашать управляющих могут только администраторы.

### TLS и сертификаты

Проверка TLS всегда включена. Если системное хранилище не доверяет сертификату MAX API, получите доверенный корневой CA из официального источника и укажите `MAX_CA_BUNDLE`. Не отключайте проверку сертификатов.

Если нужен дополнительный CA, PEM-файл должен быть доступен внутри контейнера
`app`. Это необязательное расширение требует файла сертификата в дополнение к
двум основным файлам. Добавьте mount в `compose.yml`, например:

```yaml
services:
  app:
    volumes:
      - ./certs/max-ca.pem:/certs/max-ca.pem:ro
    environment:
      MAX_CA_BUNDLE: /certs/max-ca.pem
```

Значение `environment` имеет приоритет над пустым `MAX_CA_BUNDLE=` в `.env`.
После изменения CA пересоздайте контейнер:

```bash
docker compose up -d --force-recreate app
```

`ConnectTimeout` во время TLS handshake означает таймаут соединения, а не ошибку доверия CA. Проверьте исходящий HTTPS, DNS и настройки proxy с хоста или из контейнера. Не отключайте проверку TLS.

### Диагностика бота

- `GET /updates -> 200` подтверждает успешный HTTPS-запрос и доступ к обновлениям. Последующий `POST /messages -> 404` - отдельная ошибка отправки. Бот пишет HTTP-статус MAX, `code` и `message`, но не выводит токен и содержимое обновления.
- Личные ответы (`bot_started` и сообщения с `chat_type=dialog`) отправляются по ID пользователя. Групповые ответы отправляются по ID чата. Не подставляйте ID пользователя в `chat_id` для группового сообщения.
- Постоянные ошибки отправки `4xx` пропускаются, чтобы одно событие не блокировало очередь. Для `401`, `408`, `429`, сетевых ошибок и `5xx` marker не продвигается, запрос повторяется. При повторе пачки уже отправленные приветствия могут дублироваться.
- Запросы сканеров к `.env` не связаны с MAX. SPA fallback может вернуть HTML приложения с кодом `200` для неизвестного пути; это не доказывает утечку файла. Nginx явно возвращает `404` для скрытых файлов и каталогов.

### Авторизация и Bridge

Frontend передаёт серверу необработанный `window.WebApp.initData`. Сервер проверяет двухэтапную подпись HMAC-SHA256, срок действия в один час, дубли параметров и ID пользователя. `initDataUnsafe` не используется для авторизации. После входа JWT хранится в `sessionStorage`. WebSocket использует отдельный ticket со сроком действия одну минуту, а не токен в URL.

Подключён официальный MAX Bridge (`https://st.max.ru/js/max-web-app.js`). Поддерживаются BackButton, подтверждённый номер телефона и скачивание вложений. В обычном браузере вложения открываются обычными ссылками; MAX требует HTTPS для скачивания.

Официальная документация: [Bridge](https://dev.max.ru/docs/webapps/bridge/), [валидация](https://dev.max.ru/docs/webapps/validation/), [Mini Apps](https://dev.max.ru/docs/webapps/introduction/), [Bot API](https://dev.max.ru/docs-api/).

## Проверки

Запустите проверки backend из корня репозитория:

```bash
uv run --directory backend python -m pytest -q
uv run --directory backend ruff check app migrations tests
```

Запустите проверки frontend из каталога `frontend`:

```bash
cd frontend
npm test
npm run build
```

Backend-тесты используют временную SQLite и тестовые credentials. Они не обращаются к MAX и не изменяют рабочую базу. Проверяются авторизация, подписи, сидер, идемпотентность начислений, конкурентная проверка заданий, доработка, приглашения, модерация, мероприятия, дуэли и циклы миграций. Frontend-тесты проверяют изоляцию сессий после выхода и повторного входа.

## Ограничения

- Дуэль учитывает только академические начисления за задания и мероприятия внутри её временного окна и учреждения. PvP-бонусы не влияют на счёт дуэли. Награды и начисления идемпотентны.
- Даты API передаются с часовым поясом и нормализуются в UTC. Интерфейс показывает местное время.
- SQLite использует WAL и сериализацию бизнес-транзакций. Прототип рассчитан на один API worker и один планировщик, а не на горизонтальное масштабирование.
- К одному материалу можно прикрепить до 10 файлов, размер каждого - до 20 МБ. Разрешённые расширения ограничены. Файлы доступны по непрогнозируемым URL `/media/...` без отдельной авторизации скачивания. Не храните конфиденциальные документы. Для production нужны ACL или подписанные ссылки, антивирус и очистка неиспользуемых загрузок.
- Уведомления реализованы внутри Mini App. Бот отправляет приветствие и кнопку запуска, но не отправляет все уведомления в личные сообщения MAX.
- Фоновые задачи, аватары и изображения из CDN, а также MAX Bridge требуют внешнего сетевого доступа. Работу с реальным MAX и доверие к CA нужно проверить с настроенным ботом.
- Начальная миграция Alembic создана на основе текущей metadata моделей. Перед изменением схемы зафиксируйте baseline и добавляйте самостоятельные версионированные миграции.

## Структура репозитория

```text
backend/app/          модели, API, бизнес-правила, бот, сидер и планировщик
backend/migrations/   миграции Alembic
backend/tests/        интеграционные и security-тесты
frontend/src/         Vue-компоненты, страницы ролей, router и хранилища Pinia
frontend/tests/       тесты жизненного цикла сессии
Dockerfile            единый образ: frontend, API, Nginx и бот
docker/               конфигурации процессов, Nginx, healthcheck и smoke test
compose.yml           один сервис app и постоянные volumes
nginx/default.conf    конфигурация прежней раздельной сборки frontend
```
